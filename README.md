# Polymarket Pair Bot — محاكاة فقط

نسخة بحثية لاستراتيجية شراء Up وDown في أسواق BTC ذات الخمس دقائق، ثم دمج
الكميات المتطابقة افتراضيًا. **لا تداول حقيقي، لا مفاتيح، لا ربط محفظة، لا توقيع.**
لا يوجد وضع `live` مخفي يمكن تشغيله بتغيير إعداد.

## التشغيل من الهاتف عبر GitHub

1. افتح **Actions → Paper bot tests** للتحقق من اختبارات الكود.
2. افتح **Public data paper session → Run workflow** واختر المدة والمشغّل (ابدأ بدقيقتين على `ubuntu-latest`).
3. انتظر النتيجة ثم افتح **Artifacts → paper-session-estimates**.
4. داخل الملف ستجد `report.html` و`summary.json` و`journal.json` وتسجيلات مضغوطة
   `events-*.jsonl.gz`؛ وعند الخطأ `errors.jsonl` مع traceback كامل.

هذا تشغيل محاكاة مؤقت ضمن حصتك في GitHub Actions، وليس استضافة مستمرة.
قد ترفض واجهات Polymarket الوصول من موقع الخادم؛ عندها تفشل العملية صراحة،
ولا نحاول تجاوز الرفض أو اختلاق بيانات. الاختبار الحسابي الناجح لا يثبت نجاح الاتصال.

## تشغيل محلي (Python 3.12+)

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m pairbot doctor
python -m pairbot paper --minutes 60
```

على Termux يلزم تثبيت Python وGit أولًا. توافق Termux لم يُختبر على جهاز فعلي.
اختر مجلد نتائج جديدًا لكل تشغيل؛ البرنامج يرفض الكتابة فوق تسجيل موجود.

للتسجيل دون محاكاة ثم إعادة الاختبار بنفس القواعد:

```bash
python -m pairbot record --minutes 60 --out runs/capture
python -m pairbot replay runs/capture --out runs/replayed
```

للتأكد من سلامة التثبيت دون إنترنت:

```bash
python -m pairbot replay examples/synthetic.jsonl --out runs/synthetic
```

**المثال synthetic بيانات مصطنعة لاختبار الحسابات، وليس تجربة ربح فعلية.**

## الاستمرارية والاستعادة

يحفظ البرنامج تقريرًا جزئيًا كل 5 ثوانٍ، ويعيد الاشتراك ويحصل على snapshots
جديدة بعد الانقطاع أو اضطراب ترتيب الأحداث. يستمر دفتر الأسعار بالتحديثات
المتأخرة المرتبة، لكن لا يستخدمها للتنفيذ ما دام عمرها يتجاوز الحد المسموح.
طلبات التسوية تعمل منفصلة عن استهلاك WebSocket. انتهاء السوق ينقل الاشتراك
للسوق التالي، مع الاحتفاظ بالبقايا حتى ظهور نتيجة رسمية.

للاستعادة من تسجيل مكتمل/متوقف بصورة سليمة، مع الاحتفاظ بالمخزون والمحاسبة:

```bash
python -m pairbot paper --resume runs/previous --minutes 60 --out runs/resumed
```

تُسجّل فجوة عند الاستعادة؛ ليست تجربة متصلة عبر فترة التوقف. يُرفض التسجيل
التالف بدل تجاهله وادعاء استعادة كاملة. الإيقاف القسري `SIGKILL` قد يقطع آخر
ملف gzip؛ تبقى التقارير الدورية مفيدة لكن لا تكفي لإعادة حساب المخزون بدقة.

المشغّل المستضاف في GitHub محدود بـ6 ساعات **للعملية كلها** بما فيها الإعداد
والرفع. لذلك أقصى اختيار مستضاف هنا 350 دقيقة مع هامش؛ لا يضمن الهامش نجاح
الرفع إذا استغرق الإعداد طويلًا. تجربة 360 دقيقة تتطلب مشغّل `self-hosted` قائمًا
ومصرحًا به، ويُرفض اختيارها على المستضاف. وجود خيار self-hosted لا ينشئ خادمًا.
[حدود GitHub الرسمية](https://docs.github.com/en/actions/reference/limits).

اختبار `Multi-market live validation` يبدأ يدويًا فقط، ويلتقط 11 دقيقة
عامة حية ويختبر انتقال 3 أسواق وإعادة التشغيل الحتمية، ثم يحفظ artifact.
رفض الوصول يفشل الاختبار صراحة. التسجيل لا يثبت الربحية، خصوصًا دون fills.

## القواعد الحالية

الإعدادات في `config/paper.toml`: رأس مال افتراضي $50، حجم أمر 5 أسهم، حد
تكلفة المخزون والأوامر والمبالغ المعلقة $15، وحد خسارة للجلسة $2.50.
الحد الأخير يوقف فتح الأوامر؛ ليس ضمانًا بألا تتجاوز الخسارة هذا الرقم.

- نحتفظ بدفتر حقيقي مستقل لكل طرف؛ لا نشتق سيولة Down من سعر Up.
- دورة واحدة في كل مرة. البداية بعرض شراء للطرفين وحجز تكلفتهما؛ التنفيذ قد يحدث
  في أوقات مختلفة. فوق البقايا نعرض الطرف الناقص فقط، ضمن سقف التكلفة والمهلة
  والحد الأدنى للسوق. البقايا الصغيرة لا تُضخّم لفتح أمر جديد.
- تكلفة الزوج المستهدف تراعي رسوم Maker وتكلفة الدمج المحددتين بالإعدادات.
- الأوامر افتراضيًا post-only، مع تأخر وصول وإلغاء وتنفيذ جزئي.
- كل 10 ثوانٍ نراجع الأمر: إذا بقي السعر مناسبًا والبيانات حديثة نحافظ عليه
  وعلى طابوره؛ إذا تغير الهدف نلغيه بالتأخير المحدد. لا تتحسن أولوية الطابور
  لمجرد اختفاء سيولة من الدفتر.
- حركة 3 سنتات توقف الاقتباس مؤقتًا. نعيد التقييم بعد 15 ثانية من التهدئة
  واستقرار مشاهد في نافذة 5 ثوانٍ؛ الصدمات الجديدة تمدد التهدئة. الانقطاع
  لا يُحسب استقرارًا. هذه سياسة بحثية جديدة، وليست إعدادات ربح مثبتة.
- التنفيذ يتطلب SELL trade print عند سعر الأمر أو أدنى، وبعد استهلاك طابور
  محافظ من السيولة المرئية. لمس السعر أو اختفاء الأوامر لا يعني تنفيذًا.
- دمج الكمية المتساوية ينتظر تأكيدًا افتراضيًا قبل إعادة المال للرصيد.
- البقايا تبقى ظاهرة ولا تُحذف من الخسائر. بعد مهلة الطرف الثاني تتوقف
  الأوامر لهذا السوق وتُنتظر التسوية الرسمية؛ لا نفترض خروجًا ناجحًا.
- تسوية البقايا لا تعتمد على تخمين اتجاه BTC أو سعر 0.999: تحتاج تأكيد
  إغلاق السوق وحالة resolved ونتيجة ثنائية نهائية. غيابها يبقي المخزون معلقًا.
- الرسوم إعدادات بحثية وليست قراءة آلية مضمونة للرسوم الحالية. المكافآت صفر.

## قراءة النتيجة بصدق

`paired_pnl` ربح الأزواج بعد تأكيد الدمج، و`residual_pnl` نتيجة البقايا المسوّاة.
`pnl_marked` يستخدم تقييمًا محافظًا بعمق الطلبات المتاح، ويقيّم العمق المفقود بصفر.
`pnl_realized` لا يشمل المخزون غير المسوّى. راقب `unsettled_shares` و`pending_merges`.
`final_pnl_available=false` يعني أن النتيجة لم تكتمل. `NO_DATA` يعني عدم توفر بيانات،
وليس إثبات نتيجة صفر. `INCOMPLETE_DATA` يمنع اعتبار التشغيل اختبار تنفيذ موثوقًا.

المحاكاة تقديرية: البيانات العامة لا تكشف ترتيبنا الحقيقي ولا السيولة الخفية؛
والصفقات المتطابقة في التوقيت قد تُستبعد كتكرار. لا تمثل النتائج أرباحًا قابلة للتنفيذ.
انظر [حدود النموذج](docs/MODEL.md) و[حالة التحقق](docs/VALIDATION.md).

## تشخيص عدم التنفيذ — الإصدار 0.3.0

`execution_diagnostics` يعرض أسباب منع فتح الأوامر وأسباب تجاهل الصفقات،
ودورات الأوامر وتفعيلها والاحتفاظ بها والتوقف والاستئناف. عدد فحوص الشروط
ليس عدد فرص مستقلة ولا نسبة من زمن التشغيل. يطبع سجل Actions تحديثًا كل دقيقة
بعدد التعبئات والمخزون والأسباب، ويبقى التقرير الدوري كل 5 ثوانٍ.

لتحليل تسجيل قديم بالقواعد الحالية دون اتصال أو تشغيل حي:

```bash
python -m pairbot analyze runs/capture --out runs/analysis
```

التحليل يُوسم `RECORDED_PUBLIC_RESEARCH`، ولا يغير نتائج التشغيل الأصلي.
لا يمكن استئناف محاسبة إصدار قديم بقواعد إصدار جديد؛ ابدأ مجلد جلسة جديدًا.
لا نضمن تنفيذًا أو ربحًا بمجرد إصلاح البرنامج. انظر
[السبب المثبت والإصلاحات والقيود](docs/EXECUTION_REPAIR.md).
